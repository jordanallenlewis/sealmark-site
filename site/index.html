01 The problem

Agents got database access faster than anyone checked the locks.

Every MCP database server says it has guardrails. Few are tested the way agents actually use them: many tools, many roles, all day, against data that matters.

Does read-only mean read-only?

Plenty of servers ship writable by default, or enforce read-only on the query tool and forget the others.

Does row-level security survive the MCP login?

If the server connects as the table owner, every policy you wrote is quietly skipped.

Is personal data masked on every path?

Masked in the query tool and plain text in the export tool is still a leak.

Would you even know?

Without an audit row for every call, "what did the agent read last night?" has no answer.

Configuration says what should happen. Only a test shows what does.

02 The standard

Sealmark is the independent grade for agent data access.

One letter per server version, the formula that produced it, and the evidence behind every check. Anyone can rerun it and get the same answer.

Behavior over declarations.Sealmark runs the call and records what came back, instead of reading what the tool schema promises.

Evidence for every grade.Each check links to the exact probe, the response, and the command that reproduces it.

One letter, open formula.The grading formula is versioned and public. Recompute any grade from its result file.

Regraded on every release.A grade belongs to one version. Fixes show up the day they ship, and so do regressions.

Grading formula 1.0

A90% or moreReady for agents on governed data.
B75–89%Solid, with gaps to configure around.
C60–74%Needs extra controls in front.
D45–59%, or any critical failNot safe for restricted data as shipped.
FBelow 45%Basic protections missing.

Rules

  1. Points per checkpass 1, partial 0.5, fail 0. A check passes only if all three roles behave as the rubric says.
  2. Percentagepoints ÷ checks scored. Held checks are left out until their disclosure window closes.
  3. Critical capA fail on row-level security, personal-data masking, or mutating-SQL blocking caps the grade at D.
  4. Provisional markA held critical check adds * to the grade until the result is published.
  5. Per versionEvery release is regraded. Grades are never inherited.

03 Get started

Grade your first server in one command.

The harness behind the public scorecard is the same one you run locally and in CI. Requires Node.js 22 and Docker.

  1. Install and initsealmark init writes a short sealmark.yaml that names your server and the version under test.
  2. Run against the seedSealmark starts the seeded database in Docker and runs all seven checks as all three roles.
  3. Gate the release--fail-under B exits nonzero when the grade drops below B, so a regression never ships.
  4. Get listedOpen a pull request with your sealmark.yaml to the public registry. The next scheduled run grades you.
# install and grade a local server
npm i -g sealmark
sealmark init
sealmark run --fail-under B

FAQ

Questions teams ask first

Does Sealmark need access to production data?

No. By default it grades against a seeded synthetic database. On Cloud plans you can point the runner at a masked staging snapshot inside your own network; nothing leaves it.

Does an AI model decide the grade?

No. Every check is a fixed tool call compared against a published rubric. The same server version gets the same grade on any machine.

Which servers can it grade?

Any MCP server that exposes database tools over stdio or HTTP. The seed ships for Postgres first, with more engines planned.

What happens when you find a vulnerability?

The result is held and the maintainer gets a private report with the exact rerun command. It's published when a fix ships or after 90 days, whichever comes first.

Can a vendor pay for a better grade?

No. Public grades come from the public run only. See the pledge above.

Is the CLI really free?

Yes. Every check, custom policies, the CI gate, and the badge stay free and open source. Cloud plans charge for hosted operations and audit evidence, never for checks.
