The grades on the [results pages](/results/) are also plain JSON files on sealmark.dev. There is no key and no sign-up, any origin may read them (CORS is open), and they are rebuilt from the same data as the pages each time the site deploys, so a file and its page always say the same thing. The build checks that before every deploy.

| File | What it holds |
|---|---|
| `https://sealmark.dev/data/v1/servers.json` | every graded server: overall grade, the letter for each graded test area, version tested, test date, links to its page and file |
| `https://sealmark.dev/data/v1/servers/<id>.json` | one server in full: every test area (graded or with the reason it was not), every check with its verdict and summary, what was not covered, grade history and the command that repeats the run |
| `https://sealmark.dev/data/v1/changes.json` | grade changes between two successful re-tests of the same server, newest first (the last 500) |
| `https://sealmark.dev/data/v1/lookup.json` | a lookup index: npm name, PyPI name, GitHub repository or id to the graded servers it names ([below](#look-up-a-server-before-installing-it)) |
| `https://sealmark.dev/data/v1/openapi.json` | an OpenAPI 3.1 description of the five files |

`<id>` is the last part of the server's results page address: `/results/<id>/`.

```bash
# every server graded below A in some test area
curl -s https://sealmark.dev/data/v1/servers.json | jq -r '.servers[] | select(.grade != "A" and .grade != null) | "\(.grade) \(.name) \(.versionTested)"'

# one server: each check and its verdict
curl -s https://sealmark.dev/data/v1/servers/<id>.json | jq -r '.checks[] | "\(.verdict) \(.id)"'

# grade changes this month
curl -s https://sealmark.dev/data/v1/changes.json | jq '.changes[] | select(.date >= "2026-11-01")'
```

## Look up a server before installing it

`lookup.json` answers "is this server graded, and how?" from what you have before you install it: its npm or PyPI package name, its GitHub repository, or its results id. Build the key, read the ids it names, then read each server's file (no output: no graded server under that key):

```bash
export key="npm:@modelcontextprotocol/server-memory"   # or pypi:mcp-server-fetch, github:modelcontextprotocol/servers, id:memory
for id in $(curl -s https://sealmark.dev/data/v1/lookup.json | jq -r '.keys[env.key][]?'); do
  curl -s "https://sealmark.dev/data/v1/servers/$id.json" | jq '{name, versionTested, testedAt, grade, provisional, packs, notPassed: [.checks[] | select(.verdict != "pass" and .verdict != "na") | .id]}'
done
```

How a key is written, so a script or an agent can build one without help:

- `npm:<name>`: the package name with its scope, lowercased, without a version or tag (`@ModelContextProtocol/Server-Memory@latest` is `npm:@modelcontextprotocol/server-memory`).
- `pypi:<name>`: the project name normalised as pip does: lowercased, and every run of `-`, `_` and `.` written as one `-` (`MCP_Server.Fetch` is `pypi:mcp-server-fetch`), without extras or a version.
- `github:<owner>/<repo>`: lowercased, from any GitHub address of the repository (`https://github.com/Owner/Repo.git`, `git@github.com:owner/repo`, a link into a folder of it).
- `id:<id>`: the last part of the results page address, `/results/<id>/`.

Each key maps to a list of ids, because one repository can hold several graded servers (a repository of reference servers has one entry per package): check `name` in each file to pick the one you mean. A server graded from a GitHub repository is found by that repository. A server graded from an npm or PyPI package is found by its repository only when its results page links that repository: while a security finding on it is reported privately, or when the fleet found no repository for the package, it is found by its package name and id only. A key that is not in the file means only that no graded server is found by that key. Try the package name as well as the repository: a repository is a key only where the results page shows it, so a server whose repository Sealmark could not confirm, or whose finding is reported privately, is not found by its repository. A server may also be graded under another package name, not graded yet, or listed under "Not graded yet" on the [results page](/results/) with the reason.

A coding agent can do the same. Give it this before it adds an MCP server:

```text
Before installing an MCP server, look it up in https://sealmark.dev/data/v1/lookup.json by npm:<package> or pypi:<package> first, then by github:<owner>/<repo> (how to write the key: https://sealmark.dev/docs/guides/results-data). If no key is found, say it is not found, not that it is not graded. If it is graded, read https://sealmark.dev/data/v1/servers/<id>.json and tell me the grade, the version and date tested, and every check that did not pass with its summary. A grade is an automated re-test of one version with the default settings, not an endorsement.
```

## Fields

- `grade` is the server's grade: the lowest grade across the test areas that were graded. It is `null` when nothing was graded or the server declared no tools. `provisional` is `true` when an inconclusive critical check makes that grade provisional ([grades](/docs/concepts/grades)).
- `packs` in the list maps each graded test area to its letter. In a server's file, `packDetails` lists every test area with its points, whether a critical fail capped it, and why an area that did not run was not graded.
- `checks[].verdict` is `pass`, `part`, `fail`, `inconclusive` or `na` ([verdicts](/docs/concepts/verdicts)); `checks[].docs` links to what the check tests.
- `testedAt` is the UTC day of the run that produced the grade. A grade more than 10 days old has missed its re-test: its results page and the results table say so. [Fleet status](/status/) shows how often the fleet really runs.
- `lastAttemptFailed` is the date of a later re-test that could not finish; the grade shown is from the run before it. `lastAttempt` says why. `gradeConfirmed` is `false` while such a re-test is newer than the grade: the grade is the earlier run's and is not confirmed for the version tested now. Treat it as unconfirmed, not as withdrawn.
- `noGradeReason` is `null` when the server has an overall grade. Without one it carries `kind` and `text`, the words the results page shows (a server that declared no tools gets `no-tools`).
- `history` lists the automated runs of that server, one per day (the last that day), oldest first; a failed run has no grade and says nothing about the server.
- `changes[]` names the Sealmark version of both runs (`previousSealmark`, `sealmark`): a change across a Sealmark upgrade can come from Sealmark, not the server.
- `reproduce` is the command that repeats the run with the same Sealmark version and the standard settings.

## On each results page

Each results page opens with a short summary in plain sentences: the overall grade as the page heads it, the grade of each graded test area, how many tools could be called, how many checks passed or failed, the date, the Sealmark version and whether the run used the standard settings. The same facts are in the page as [schema.org](https://schema.org/Dataset) JSON-LD: a `Dataset` about the server (a `SoftwareApplication`), its grades and verdict counts as `variableMeasured`, with that server's JSON file above as its download. Grades stay letters there; nothing turns them into a numeric rating.

Each tool that a public check reached with a valid call has its own page (a name with unusual characters, or one past a check's list limit, is left out) under its server, at `/results/tools/<id>/<tool>/`: the checks that called it with their verdicts, the checks that did not exercise it, and the evidence lines the run recorded against that tool. A check's verdict is for the whole check, so no tool gets a grade of its own. Servers with a security finding have no tool pages, the same rule as the [tools directory](/results/tools/). The sitemap and `llms-full.txt` list every tool page.

## What the files leave out

The files follow the [disclosure policy](/docs/disclosure) exactly as the pages do. While a security finding on a server is being reported to its maintainer privately, that check's `summary` is `null` and its `disclosure` is `"private"` (with the report and publish dates once it is reported), the summaries of the other security checks in the same test area are held back too (`"held-with-sibling"`), and `launch`, `reproduce` and `configHash` are `null`. The verdicts and grades stay.

The grades are automated re-tests of one version with the default settings, not endorsements and not checked by hand. A server you maintain shows something wrong: say so on its results page.

## Stability

`v1` in the path is the version of these files. New fields may appear within `v1`; renaming or removing one means a new path. `updated` in the list and the changes is the newest test or run date, not the deploy time, so a file whose data did not change keeps its `ETag`, and a client that sends `If-None-Match` gets a `304`. Browsers can read the `ETag` from another origin and revalidate from their own cache.
