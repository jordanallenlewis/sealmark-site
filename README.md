# sealmark-site

The website at [sealmark.dev](https://sealmark.dev) and the fleet that keeps its results current. Public. The tool itself lives in the public repository [jordanallenlewis/sealmark](https://github.com/jordanallenlewis/sealmark).

| Path | What |
|---|---|
| `web/` | Next.js static site: docs, results pages. `cd web && npm ci && npm run dev` |
| `web/content/data/server-results.json` | The one data file behind the results pages |
| `fleet/` | `plan.mjs` picks servers to re-test (new versions, stale results, a few new ones from the MCP Registry); `merge.mjs` folds the reports into the results file and `history.jsonl` |
| `web/worker/` | The Worker in front of the static site: only `/api/*`. `/api/notify/*` is the grade-change email alerts (D1 `sealmark-notify`, hourly cron); `notify-core.mjs` holds the email and issue texts. `/api/visit` counts page views with the referring host and UTM params only (`visits.mjs`, privacy note `/privacy/`) |
| `fleet/notify-owners.mjs` | One GitHub issue per server repository on its first grade; drafts in `fleet/owner-issues-draft.md` until switched on |
| `fleet/impact.mjs` | What happened to grades after owners were told, against a never-notified base rate: `fleet/impact-summary.md` (internal, not on the site) |
| `.github/workflows/fleet.yml` | Re-test every 6 hours (and by hand) on GitHub-hosted machines; commits the new grades and deploys when `CLOUDFLARE_API_TOKEN` is set. A run started by hand is a test run unless `dry_run` is unticked: owner issues are only drafted and nothing is committed, filed or deployed. `force_all` re-tests every tracked server (up to the 256-job matrix) |
| `.github/workflows/release-sync.yml` | Follows every Sealmark release (release dispatch, a 30-minute poll, or by hand): pins the CLI, regenerates the docs, commits, deploys and checks the live site |
| `.github/workflows/fleet-check.yml` | Checks changes to `fleet/` on pull requests |
| `.github/workflows/web.yml` | Build, docs checks and lint on every change to `web/` |
| `site/index.html` | The original single-file mockup |

The docs pages are generated from the published CLI: `web/package.json` pins `sealmark`, and `npm run docs:gen` reads `node_modules/sealmark`. Bump that version when a new CLI is released, then run `npm run docs:gen` and `npm run schema:sync`.

Deploys: `fleet.yml` and `release-sync.yml` deploy `main` automatically. By hand: `cd web && npm run build && npx wrangler deploy`.

Secrets: `FLEET_EXCLUDE` (a regular expression of package names the fleet must not grade), `CLOUDFLARE_API_TOKEN` (deploy: Workers Scripts edit is enough for the Worker with its D1, email and cron bindings; D1 read lets `impact.mjs` count sent emails, and without it that step only logs that it could not), the optional `SEALMARK_ISSUES_TOKEN` (files grading issues in the sealmark repository) and `OWNER_ISSUES_TOKEN` (owner issues, below).

Visit counts: the Worker secret `VISITS_TOKEN` (not a repository secret) guards the owner's report, `GET https://sealmark.dev/api/visits?days=30` with `Authorization: Bearer <token>` (JSON: visits per day, UTM sources, referring sites, pages, the last 50 landings). Rows hold the page, the referring host and the UTM params, nothing else, and are deleted after 365 days. Migration `0003_visits.sql` is applied with `npx wrangler d1 migrations apply sealmark-notify --remote`.

Owner notices:

- **Email alerts** (results-page form, double opt-in): on. The Worker secret `NOTIFY_SECRET` is set and `vars.NOTIFY_LIVE` in `web/wrangler.jsonc` is `"1"`; they send from `grades@notify.sealmark.dev`. Kill switch: set `NOTIFY_LIVE` to `"0"` and deploy, and every email is logged instead of sent. Privacy note: `/notify/`.
- **GitHub issues to owners**: posted by the Sealmark bot account ([`sealmark-bot`](https://github.com/sealmark-bot)), never a personal one; the script refuses a token that belongs to an account in `SELF`. The bot account's token is the secret `OWNER_ISSUES_TOKEN`. It must be able to open issues on other people's public repositories: a classic token with the `public_repo` scope (a fine-grained token only reaches repositories the account owns or belongs to). Until it is set, `fleet/owner-issues-draft.md` shows what would be filed.
  - The first batches are approved by hand: read the draft on `main`, then run the fleet workflow by hand with `file_owner_issues` ticked and `dry_run` unticked. That run posts only the `## owner/repo` entries of the committed draft, and only those whose issue still renders byte for byte as drafted (a re-test in between skips that repository, and the log says why).
  - With the repository variable `OWNER_ISSUES_LIVE` set to `1` every fleet run files on its own (the steady drip, live since 2026-11-17). `fleet/owner-pick.json` (`{"repos": [...]}`) is only for extra hand-picked batches: those repositories go first; it never limits the drip.
  - Rate limits, all in `fleet/owner-limits.mjs` and pinned by `fleet/owner-limits.test.mjs`: at most `MAX_OWNER_ISSUES` per run (2), `MAX_OWNER_ISSUES_PER_DAY` in a rolling 24 hours (6) and `MAX_OWNER_ISSUES_PER_WEEK` in a rolling 7 days (30), at least `OWNER_ISSUE_GAP_MINUTES` (30) since the last notice before a run posts, 2 minutes between posts inside a run, the caps also checked against the bot's real issue count read from GitHub (a ledger commit that never lands cannot raise them), one notice per repository owner per 7 days, one issue per repository ever. All are repository variables; a malformed value keeps the default and `0` pauses. The token is checked with `GET /user` every run; a 401 warns and nothing is posted.
  - Stop switches: any 403, 429 or rate-limit answer pauses posting for 24 hours (`ledger.pause`). A negative reaction to any notice pauses it until a person clears `pause` in `fleet/owner-notified.json`: the issue closed as not planned, removed or hidden, a thumbs-down, or a reply that says stop, spam or unsolicited. The run goes red with an `::error::` line and `fleet/owner-weekly.md` says PAUSED.
  - Only when it helps: the grade must be stable (the same version graded at least twice with the same letters, from `fleet/history.jsonl`), the notice must name at least one check that failed or partly passed, with how to fix it (the registry's remediation), so an A with nothing to fix is never told; the version tested is the current one; the repository had a commit in the last 180 days. Most helpful first: the biggest fixable gap, then the larger server.
  - No silent drops: every graded server ends up sent, waiting (with the reason and, where known, when), held or skipped (with the reason). The log's `standing of N graded servers` line and the "Where every graded server stands" tables in `fleet/owner-weekly.md` count each reason. A run that finds eligible repositories for 2 live runs in a row and sends none, with no cap, gap or pause to explain it, logs `::error::owner notices stalled` and shows Stalled in the weekly file.
  - Opt-out: every notice says to reply "opt out"; the reply is honoured automatically for every repository of that owner, forever.
  - Never on archived repos, forks, repos with issues off, our own repos, or repos in `fleet/owner-optout.json`. Only fresh grades (older than 14 days, or a failed latest re-test, waits). Also skipped, with the reason in the draft: no tools declared; no tool reached with a valid call (hygiene-only), unless the grade is an A; a grade below A that only weak signals explain; a newer version than the one tested; a launch line with harness placeholders; a package in a subfolder of a larger repository, or a repository whose root package is not the one tested. A renamed repository is followed to its canonical name.
  - Security findings never go in an issue. `fleet/security-checks.mjs` is an allowlist of the checks an issue may name; a failing or partly passing check that is not on it (a future one too) holds the whole repository. Held repositories are in `fleet/owner-private-queue.json` and `fleet/owner-private-draft.md`, which are gitignored and never sent: run `node fleet/notify-owners.mjs --dry` locally to see them and report them by hand under the [disclosure policy](https://sealmark.dev/disclosure/).
  - Private reports (`fleet/private-reports.mjs`, off until `OWNER_PRIVATE_LIVE` is `1` and the secret `OWNER_PRIVATE_KEY` exists): for a held repository that has GitHub private vulnerability reporting on, whose grade is fresh and stable, whose tested version is current and whose launch line runs as written, the bot files a private report (`POST /repos/{repo}/security-advisories/reports`) under the disclosure policy: 14 days to reply with one reminder, publication at a fix or at day 90. Caps `OWNER_PRIVATE_PER_RUN` 1, `_PER_DAY` 2, `_PER_WEEK` 7, an hour apart; the same pause applies. The ledger keeps only a keyed hash (HMAC with `OWNER_PRIVATE_KEY`) of each repository reported, the log and weekly file give counts only, and the exact text of the next reports is written to the gitignored `fleet/owner-private-reports.md` for review. Repositories without private reporting stay held.
  - Replies: every run reads the comments on the bot's issues. Replies from people go to `fleet/owner-weekly.md`, the run summary and one tracking issue here, "Owner replies to Sealmark issues"; removal and recheck requests are listed first.
  - `fleet/owner-weekly.md` (rewritten each week and when a reply arrives, also in every fleet run's summary) counts issues opened, replies, opt-outs, grade-change emails and letter moves since the notice.
